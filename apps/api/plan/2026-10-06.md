# Ledgerly Code Task Plan - 2026-10-06

## Goal

Add Ledgerly's first authentication and authorization implementation.

By the end of this phase, users should be able to register, log in, authenticate with a JWT access token, retrieve their authenticated identity, and interact only with accounts they own.

## Database And Schema Tasks

- [ ] Add `passwordHash` to the Prisma `User` model.
- [ ] Create the necessary Prisma migration.
- [ ] Regenerate Prisma Client if required.
- [ ] Update existing code affected by `passwordHash` becoming a required User field.
- [ ] Confirm existing User -> Account relationships still work after the migration.

## Authentication Structure Tasks

- [ ] Create the authentication module.
- [ ] Create `AuthController`.
- [ ] Create `AuthService`.
- [ ] Wire the authentication module into the application.
- [ ] Add the required authentication/JWT dependencies.
- [ ] Add JWT configuration.
- [ ] Move the JWT signing secret into environment/configuration rather than hard-coding it.

## Registration Tasks

- [ ] Create `RegisterDto`.
- [ ] Add validation rules for registration input.
- [ ] Add `POST /auth/register`.
- [ ] Check for an existing user with the submitted email.
- [ ] Hash the submitted password before persistence.
- [ ] Store only `passwordHash`.
- [ ] Ensure the plain-text password is never persisted.
- [ ] Ensure `passwordHash` is not returned in the registration response.
- [ ] Return `409 Conflict` for duplicate email registration.
- [ ] Return `400 Bad Request` for invalid registration input.

## Login Tasks

- [ ] Create `LoginDto`.
- [ ] Add validation rules for login input.
- [ ] Add `POST /auth/login`.
- [ ] Find the user by email.
- [ ] Verify the submitted password against the stored password hash.
- [ ] Return the same authentication error for nonexistent users and incorrect passwords.
- [ ] Create the JWT payload.
- [ ] Sign the JWT access token.
- [ ] Add an expiration time to the access token.
- [ ] Return the access token after successful authentication.
- [ ] Return `401 Unauthorized` for invalid credentials.

## Authentication Guard Tasks

- [ ] Implement JWT extraction from the `Authorization: Bearer <token>` header.
- [ ] Verify incoming JWT access tokens.
- [ ] Reject missing tokens.
- [ ] Reject invalid tokens.
- [ ] Reject expired tokens.
- [ ] Make the authenticated user's identity available to protected request handlers.
- [ ] Create/configure the authentication guard.
- [ ] Keep authentication verification logic out of individual controllers.

## Current User Tasks

- [ ] Add `GET /auth/me`.
- [ ] Protect `GET /auth/me` with authentication.
- [ ] Obtain the current user's identity from the authenticated request.
- [ ] Return the authenticated user's public information.
- [ ] Ensure `passwordHash` is not returned.

## Account Ownership Changes

- [ ] Protect `POST /accounts`.
- [ ] Remove `userId` from `CreateAccountDto`.
- [ ] Reject client-supplied `userId` according to the application's validation configuration.
- [ ] Obtain the account owner's ID from the authenticated user.
- [ ] Create new accounts for the authenticated user.
- [ ] Continue defaulting account balance to `0`.

- [ ] Protect `GET /accounts`.
- [ ] Remove the normal customer `userId` query filter.
- [ ] Obtain the user's ID from authentication.
- [ ] Return only accounts owned by the authenticated user.

- [ ] Protect `GET /accounts/:id`.
- [ ] Continue validating the account ID with `ParseIntPipe`.
- [ ] Check account ownership before returning the account.
- [ ] Prevent User A from retrieving User B's account.
- [ ] Use the chosen `403 Forbidden` or `404 Not Found` ownership-error strategy consistently.

## Existing User Endpoint Tasks

- [ ] Decide the final behavior of `POST /users`.
- [ ] Ensure `POST /users` does not remain a second unrestricted customer-registration endpoint.
- [ ] Reuse existing user-creation logic where appropriate instead of duplicating it inside authentication code.
- [ ] Confirm existing `GET /users/:id` behavior is not unintentionally broken.

- [ ] Plain-text passwords are never persisted.
- [ ] Password hashes are never exposed through normal API responses.
